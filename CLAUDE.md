## Commands

All commands go through `nix-shell` via the `justfile`. Avoid `cargo` directly unless you have the runtime libs from `shell.nix` already in scope.

- `just` / `just run` — debug build, runs the app
- `just release` — `cargo run --release`
- `just check` / `just clippy` (`-D warnings`) / `just fmt`
- `just build` — release binary
- `just logout` — wipe pending and per-account credentials to force re-auth

`just test` runs the unit tests (~50 in-crate `#[cfg(test)]` modules — parsers, providers, mail cache, outbox, block editor, Blitz rendering, i18n). The recipe takes no argument: to run a single test or module, call cargo inside the shell yourself — `nix-shell --quiet --run "cargo test blitz_body"`, `… "cargo test operation_store::tests::retry -- --nocapture"`.

Linting = `just clippy`; both recipes cover `--all-targets`, and the project must always pass with `-D warnings`. CI (`.github/workflows/ci.yml`) runs `cargo fmt --check`, that clippy invocation and `cargo test` inside the same `nix-shell`, plus a standalone job that diffs the key sets of `assets/i18n/fr.json` and `en.json` (a Python snippet — no Rust build needed, so a missing translation fails in seconds).

The Azure AD app `client_id` + `tenant` are bundled as `auth::DEFAULT_CLIENT_ID` and `auth::DEFAULT_TENANT` constants. The default registration is multi-tenant + public client; users in restrictive tenants can override either value via **Préférences → Comptes → Configuration Azure (avancé)**, persisted in `settings.json` as `Settings.global.azure_client_id` / `azure_tenant` (empty string ⇒ use default). The effective values are passed in with `Cmd::StartLogin { client_id, tenant }` and persisted onto the issued `Tokens` so each account refreshes against the registration it was authenticated with, even if the override is changed later.

`auth::DEFAULT_GOOGLE_CLIENT_ID` / `DEFAULT_GOOGLE_CLIENT_SECRET` are the Gmail equivalent — a "Desktop app" registration, whose secret Google's installed-app flow still requires in the code exchange (PKCE carries the actual security; RFC 8252 classes a native app as a *public* client that cannot hold a secret at all). **Both are injected at build time** via `option_env!("AVIARY_GOOGLE_CLIENT_ID"/"AVIARY_GOOGLE_CLIENT_SECRET")` rather than written in the sources, and the secret's fallback is the empty string. This buys no confidentiality — anyone can read it out of a shipped binary — but the repository is public, and a literal `GOCSPX-…` there is picked up by secret scanners and liable to be revoked under us, which would break every signed-in Gmail account at its next refresh. It also makes the secret rotatable without a source change, and lets distro packagers build without one. `.github/workflows/release.yml` supplies it from repository secrets; a local `cargo build` gets an empty secret.

Users substitute their own registration via **Préférences → Comptes → Configuration Google** (`Settings.global.google_client_id` / `google_client_secret`), which is what a build with no bundled secret, and a tenant blocking unverified apps, both need. `AviaryApp::start_google_login` requires **both halves** to be non-empty before dispatching: checking only the id would pair a user's own client id with whatever secret the binary shipped and fail at the code exchange with a message from Google rather than from Aviary.

Independently of all this, `gmail.modify` is a Google **restricted** scope: until the app passes OAuth verification (which includes a third-party security audit), the bundled registration is capped at 100 test users. That ceiling belongs in the README, not in a surprise for the 101st user.

The UI supports **French and English** through `rust-i18n` (`assets/i18n/fr.json` and `en.json`). All user-visible labels, buttons, status messages, provider errors, placeholders, and generated reply/forward text must use `tr!` (the macro is defined in `main.rs`); never hardcode UI copy. **`tr!` yields a `SharedString`, not a `String`**: the catalogs are compiled into `Cow::Borrowed(&'static str)`, so a key without interpolation costs no allocation at all — which matters because a frame renders hundreds of them. It derefs to `str`, formats and compares like one; the few call sites that must own a `String` (an input placeholder stored as such, a body assembled piece by piece, an `Evt` payload) say so with `.to_string()`. Keep both catalogs key- and placeholder-compatible (covered by `ui::i18n_tests` *and* the CI job above) and use rust-i18n's `%{name}` placeholder syntax in the catalogs. **Préférences → Apparence → Langue** applies the language immediately to every open window and persists `Settings.global.language`; `Système` resolves through `sys-locale` with environment-variable fallback.

## Privacy and test data

Never copy user-provided or real-world sensitive data into source code, tests, fixtures, snapshots, logs, comments, examples, documentation, or commit messages. This includes personal names, email addresses, phone numbers, physical addresses, account or tenant identifiers, message contents, company or client names, domains, URLs, and credentials.

Use unmistakably synthetic, role-based placeholders (`Contact A`, `Organisation de test`) and reserved domains (`example.com`, `example.test`, `example.invalid`). Before keeping a fixture derived from an email, screenshot, bug report, or conversation, reduce it to the minimum structure the test needs and anonymize every identifying value. Never reuse details supplied by a user, even when they look public.

## Architecture

Desktop email/calendar/kanban client supporting **Microsoft 365** (Graph API + device-code OAuth), **Gmail** (Gmail/Calendar/People APIs + PKCE loopback OAuth) and **IMAP/SMTP**, built on **gpui 0.2** (Zed's UI framework) + **gpui-component 0.5** (widgets: inputs, resizable panels, menus, dialogs, notifications, markdown/html `TextView`, theming). The providers are abstracted behind a `Provider` enum (`crate::model::Provider`); every backend call dispatches through `providers::*` (see "Provider abstraction" below).

`MessageHeader::conversation_id` carries the thread. It lives on the *header*, not on `Message`, because the message list never loads bodies: grouping a folder by conversation has to work from listing data alone. Ids are only comparable **within one account**, so every consumer keys on `(account_id, conversation_id)`.

`MessageHeader::internet_message_id` (RFC 5322 `Message-ID`) identifies the **mail**, where `id` identifies one mailbox copy of it. Thread queries span folders — Graph filters over `/me/messages`, IMAP searches inbox + Sent — so a mail you sent comes back twice, with two provider ids and one `Message-ID`. `viewer::thread_without_duplicates` is what keeps the reader from listing the message it is already displaying. Gmail leaves it `None` (its thread API returns each mail once); consumers must fall back to `id` rather than treating two `None`s as equal.

### Two-thread Cmd/Evt loop

The single most important pattern: the UI never does I/O. `runtime::spawn` starts a dedicated OS thread hosting a current-thread Tokio runtime, and the UI talks to it through unbounded mpsc channels:

- UI → background: `runtime::Cmd` (StartLogin, Refresh, OpenMessage, SendMail, LoadCalendar, LoadContacts, LoadSenderHistory, …)
- background → UI: `runtime::Evt` (DeviceCode, Authenticated, Messages, MessageOpened, Thread, Contacts, MailSent, Error, …)

`AviaryApp::new` spawns a foreground task (`cx.spawn_in`) that `await`s `evt_rx.recv()`, drains whatever the runtime has already produced (up to `EVENT_BATCH_LIMIT`) and calls `handle_event(evt, window, cx)` + `cx.notify()` for each event of the batch. Events arrive in bursts — a listed page, a rehydrated thread, an outbox drain — and one `update_in` per event meant one gpui effect flush per event. **When you add a new async operation, follow this pattern**: define a `Cmd` variant, dispatch it via `tokio::spawn` in `runtime::run`, and emit `Evt`s back — never block the UI thread, never call `reqwest` from the UI side.

`BgAccount::ensure_auth` transparently refreshes the OAuth access token (30-second grace window) before any provider call. New background functions should always call it (usually via `auth_or_report`) instead of touching `state.tokens` directly.

Runtime layout: `runtime/protocol.rs` holds the pure data protocol — `Cmd`, `Evt`, and the composite payloads `OutgoingMail` (SendMail/SaveDraft), `EventDraft` (CreateEvent) and `QuickActionExecution`, each with a borrowed view (`as_outgoing`/`as_new_event`) toward the provider types. `runtime/mod.rs` keeps `spawn`, `BgGlobal`/`BgAccount` and the `run()` dispatch loop (`BgGlobal::spawn_on` resolves the account and spawns the task). Per-domain tasks: `mailbox.rs`, `send.rs`, `folders.rs`, `tags.rs`, `calendar.rs`, `contacts.rs`, `sender_history.rs`, `auth_flow.rs`. Cross-cutting infrastructure on `BgGlobal`: `mail_cache.rs` (SQLite cache), `operation_store.rs` + `operations.rs` (durable outbox), `ical.rs` (`IcalManager`, subscribed feeds), `languagetool.rs` (`LanguageToolManager`, owns the Java child) and `ai.rs` (streaming writing assistant).

`BgGlobal` also serializes the single-reader requests: `message_open_task` / `message_thread_task` hold the in-flight `JoinHandle`, so opening another message cancels the previous provider call instead of racing it into the viewer.

### Local cache and durable outbox

Two SQLite databases on the config dir, both owned by dedicated actor threads (a `mpsc` command channel + `oneshot` replies) so neither the gpui thread nor the Tokio runtime ever blocks on disk:

- **`mail-cache.sqlite3`** (`runtime/mail_cache.rs`, `SCHEMA_VERSION = "7"`) — headers, bodies, pagination cursors, recipient usage, full-text index, per-thread counts. Disposable: it may be cleared or recreated after a schema bump, and its size cap is `Settings.global.mail_cache_limit_mb` (500 MB default). Message metadata is JSON, but inline images and attachment bytes are normalized into `BLOB` tables; the current header is stored separately from the body so syncing flags/tags never rewrites a large body document. Mailbox listing is **cache-first**: `mailbox.rs` emits the cached page immediately, then reconciles with the provider (`sync_cached_folder`).
  - **Search is cache-first too** (`messages_fts`, an FTS5 table). It is `content=''` (contentless: inverted index only, never a second copy of the text, which matters under the size cap) with `contentless_delete=1`, addressed by `messages.rowid` — stable across the `ON CONFLICT DO UPDATE` upserts — so hits join straight back onto `messages`. Columns are `subject, sender, recipients, body`; tokenizer `unicode61 remove_diacritics 2`, so "reunion" finds "Réunion". Indexing is explicit in Rust (`index_message`) because body text must be stripped of Markdown link targets first (`searchable_body_text`, capped at `MAX_INDEXED_BODY_BYTES`); **deletion is a SQL trigger** (`messages_fts_delete`) since messages are removed from half a dozen call sites. Listing a folder indexes subject + sender + preview, opening a message adds its body and recipients (so `à:` only matches opened messages), eviction drops the body but keeps the header searchable. `mailbox::search_messages` emits the local hits, ranked by `bm25`, then reconciles with the provider; offline it stays silent instead of contradicting on-screen results with an error toast.
  - **Thread counts come from here too.** `messages.conversation_id` is a real column (fed by `store_headers`/`store_message`), and `conversation_totals` aggregates it over `folder_messages`, excluding threads of a single message. A listed page holds a few dozen messages while a thread often spreads well beyond it, so counting in the UI would make a group's counter climb as the user scrolls. `mailbox.rs` emits the result as `Evt::ConversationTotals` after every listing; since `store_headers` and this query travel the same actor channel, the counts always observe the page stored just before.

### Search operators (`src/search_query.rs`)

The search field is parsed **once**, into `SearchQuery` — pure data, no I/O — and every consumer renders it into its own dialect, which is what makes `de:alice` mean the same thing whether the cache or a provider answers: `fts_match_expression` (FTS5 column filters), `gmail::messages::search_expression` (`q`), `graph::messages::search_expression` (KQL `$search`), `imap::messages::search_keys` (RFC 3501 `SEARCH`). Operators are accepted in French and English (`de:`/`from:`, `objet:`/`subject:`, `à:`/`to:`, `avec:pj`/`has:attachment`, `est:non-lu`/`is:unread`, `est:suivi`/`is:flagged`, `avant:`/`before:`, `depuis:`/`after:`, dates as `YYYY-MM-DD`, `DD/MM/YYYY`, `7j`, `hier`…).

Two rules hold the design together. **Unknown operators stay free text** — `truc:machin` and `Re: contrat` are searched, not rejected; a search box that errors is worse than one that searches what was typed. And **backends are never trusted to filter**: each drops what its dialect cannot express (Graph rejects `$search` combined with a date `$filter`, IMAP has no attachment predicate), so `runtime::mailbox::search_messages` re-applies `SearchQuery::matches` to every result — without it, `avec:pj` would quietly return messages without one. Adding an operator means extending the parser plus the four renderers; the local filter is the safety net for whatever a backend ignores.
- **`operations.sqlite3`** (`runtime/operation_store.rs`, `SCHEMA_VERSION = 1`) — deliberately separate, because an unsent message or an acknowledged local mutation must survive what the cache may throw away. `OperationKind` covers `Delete`, `Move`, `SetFlag`, `MarkRead`, `Send` and `QuickAction`.

`runtime/operations.rs` is the only submission path: `submit()` enqueues then drains, `schedule_quick_action()` enqueues with an `execute_at` in the future. That deferred deadline is also how the undo windows work — `Settings.global.action_delay_secs` (move/delete/tag/read/follow-up) and `send_delay_secs` — the notification's "annuler" simply cancels a row before it comes due. Drains are serialized per account (`account.operation_drain` mutex), retried with exponential backoff up to `MAX_MUTATION_ATTEMPTS = 8`, and re-armed by `arm_retry_timer` on the store's earliest deadline (nothing else polls the outbox, so without it a failed send would sit until the next manual refresh).

**A `Send` that was in flight when the process died is never replayed.** `take_interrupted` surfaces it as `Evt::MailSendError { … "outbox-delivery-uncertain" }` (or `Evt::QuickActionSendUncertain`) and lets the user decide, because the provider may already have delivered it. Keep that property when touching this code. Failed mutations emit `Evt::MutationFailed` with the cached header so the UI can roll its optimistic update back.

**One row per message means one reply per message, and a batch rarely ends cleanly.** Deleting thirty messages — or a conversation, which is the same thing seen from the list — comes back as thirty independent replies, each free to succeed, fail permanently or be deferred; seven moved and three refused is the outcome that actually happens. `BulkCompletions` (`ui/app.rs`) folds them into one: it counts both sides, keeps the **first** provider error verbatim, and hands the reply that empties the batch a `BulkCompletion` that `ui/events/outbox.rs` turns into a single toast (all through / none through / partial, summary in the title and the provider's words underneath). A batch is registered **when its commands are submitted**, in `schedule_action`, never when they are scheduled: an action cancelled inside its undo window sends nothing, so it has no batch to clean up, and the member list is derived from the commands themselves rather than passed alongside them. The aggregation is dropped after `BULK_COMPLETION_TTL` (20 min, a memory guard sized above the outbox's ~10 min of backoff, not a deadline). Same mechanism, two consequences worth keeping: only the first deferral of a batch is toasted, and a batch reloads folders and the listing once, on its last reply.

### UI module layout (`src/ui/`)

`AviaryApp` (in `ui/app.rs`) is the root gpui `Entity` holding all UI state. Each view adds its render methods in its own file via `impl AviaryApp` blocks:

- `app.rs` — the `AviaryApp` struct, its construction (event/tray pumps, input subscriptions), command helpers (`send`, `send_refresh`, `switch_to_account`, `select_folder`, `open_message`, …) and the window chrome (topbar `TitleBar` + `TabBar` Courrier / Calendrier / Kanban / Contacts / Préférences, account switcher, `Render` impl re-emitting the `Root` layers).
- `state.rs` — pure UI state types: `AuthState`, `MainView`, `ThreadBodyState`, `MailboxState` (including `open_tabs`/`active_tab` for the viewer tabs, with `ViewerTab::Loading(MessageRef)` for a session reference being rehydrated), `SenderHistoryState`, `ContactsState`. `MailboxState::selected` and `ViewerTab::Message` hold an **`Rc<Message>`**: the reader hands the displayed message to a dozen sub-elements on every frame, and a `Message` owns its body, its inline images and its attachment bytes — copying that behind each frame of a hover transition was megabytes of churn. Mutate through `MailboxState::selected_mut` / `ViewerTab::message_mut`, which go through `Rc::make_mut`.
- `events.rs` + `events/` — the receiving half of the Cmd/Evt pair. `events.rs` keeps `handle_event` (per-account relevance filter, `event_account_id`) and `handle_tray`; the reducers are split by domain into `events/{accounts,mailbox,folders_tags,calendar,contacts,compose}.rs`.
- `shortcuts.rs` — main-window key bindings (`actions!` + `KeyBinding`s) and the optional Vim-style single-key commands, active only when `vim_keybindings` is on and no field, rich editor or modal has focus. Compose shortcuts (`Ctrl/Cmd+Enter`, `Ctrl/Cmd+S`) are registered here but handled by `ComposeView` / the inline reply, whose key context is more specific.
- `auth_view.rs` — login screens (device code, Google redirect, IMAP form).
- `inbox/` — 3-pane mail view built with `h_resizable`/`v_resizable`. `mod.rs` = the panes container + sender-history pane; `folders.rs` = single-account list or unified per-account tree, context menus, create/rename/delete dialogs. Ce volet est lui aussi **virtualisé** (`v_virtual_list`) : `build_folder_entries` aplatit favoris et arbres de comptes en `FolderEntry` porteurs d'*identités* (`(compte, dossier)`), le rendu d'une ligne relisant sélection, non-lus et état hors ligne. Contrairement à la liste de messages, **seules les hauteurs sont mises en cache** (`FolderListMetrics`, clé = échelle d'interface) : l'arbre dépend d'une demi-douzaine de réglages et se reconstruit pour rien de cher, alors que le mettre en cache imposerait une invalidation à retenir à chacun d'eux. Tout espacement vertical vit dans le *wrapper* de l'entrée (`folder_list_item`) et jamais en marge : `layout_as_root` mesure la boîte du nœud, donc une marge manquerait à la hauteur réservée par la liste; `message_menu.rs` = les menus d'une ligne de message : le menu contextuel (clic droit) et le sous-menu « déplacer » partagé avec la barre groupée (`MoveScope` : même hiérarchie de dossiers pour un message et pour une sélection, seule l'action feuille diffère). `messages.rs` = search input + `message_row` (reused by sender history and the Contacts view) + "Charger plus". La liste des messages est une **liste virtualisée** (`v_virtual_list` de gpui-component) : l'arbre sections (épinglés / par jour) → lignes est aplati en `MsgEntry` de hauteur connue, un représentant de chaque *variante* (`MsgEntryVariant`) étant mesuré hors écran par `layout_as_root` (même approche que le composant `List` de gpui-component). **La clé de variante est dérivée des champs mêmes sur lesquels le rendu branche** : une différence visuelle absente de cette clé décalerait silencieusement toute la liste. La liste est **regroupée par conversation** (réglage `group_by_conversation`, activé par défaut ; les résultats de recherche restent à plat) : `group_message_items` — fonction libre, donc testable sans contexte gpui — replie les en-têtes sur la clé `(account_id, conversation_id)`, un fil prenant la place de son message le plus récent ; un fil réduit à un seul message chargé reste une ligne ordinaire. La ligne de groupe *est* ce message le plus récent, rendue par le même `message_row_inner` (donc mêmes actions rapides et survol) avec un chevron qui déplie (`expanded_conversations`, persisté en session) et une pastille de compteur ; sélection et épinglage y portent sur tout le fil, et **son menu contextuel agit sur le fil** quand elle est repliée (supprimer, archiver, déplacer, lu/non lu, épingler passent par les variantes groupées, avec le nombre de messages dans le libellé ; ouvrir, répondre, transférer et les actions rapides restent sur le message, et **les étiquettes aussi** — une étiquette alimente le Kanban, en poser une sur un fil distribuerait une carte par message). Une ligne dépliée redevient une ligne ordinaire : ses membres sont à l'écran, chacun avec son propre menu. Ouvrir une ligne repliée **marque lus ses membres chargés** (`collapsed_conversation_members` + `mark_conversation_read`) — la ligne porte la marque de non-lu du fil, n'en lire que le message le plus récent la laisserait en gras sans rien à lire à l'écran. Ce marquage vit dans `open_message` et dans le différé de `open_message_debounced`, **pas dans le gestionnaire de clic** : j/k qui traverse la liste ne doit pas lire les fils qu'il survole, et c'est le différé qui décide déjà d'une ouverture. Il est silencieux et sans fenêtre d'annulation (effet de bord de lecture, comme celui que le runtime applique au message ouvert), mais passe par l'agrégation de lot ci-dessus pour qu'un échec ne produise pas un toast par membre. `navigable_message_targets` (j/k) est reconstruit **à partir des entrées** plutôt que recalculé en parallèle, et Shift+clic suit `ordered_visible_message_references` — le regroupement fait remonter les messages anciens sous leur cadet, donc l'ordre à plat ne correspond plus à l'écran. Le préchargement « Charger plus » se déclenche par un `on_children_prepainted` sur un wrapper, en comparant l'offset (cible du lissage incluse) à `LOAD_MORE_THRESHOLD`.
- `viewer/` — the reader pane. `mod.rs` = body rendering (Fidèle/Markdown/Source — Fidèle est le défaut ; Fidèle rend le HTML original via `blitz_body.rs`, Markdown convertit le corps normalisé en HTML puis utilise le même moteur interactif, Source utilise le `TextView` public de gpui-component), tag bar, attachments, conversation thread (lazy `LoadThreadMessage`), the meeting-request panel (`render_invitation_panel`, `CalendarInvitation` + `invitation_responses_in_flight`), and `request_message_tab` (deferred open used by the kanban double-click) ; `header.rs` = tout ce qui est au-dessus du corps (objet, barre d'actions, adresses, date, contrôles d'affichage, étiquettes, panneau de pièces jointes assemblés par `render_viewer_header` ; `ViewerChrome` porte les réglages et les deux largeurs de volet sous lesquelles l'en-tête reflue) ; `attachments_panel.rs` = le panneau de pièces jointes et les récupérations derrière lui (à ne pas confondre avec `ui/attachments.rs`, les utilitaires partagés avec le composer) ; `translation.rs` = la traduction éphémère du corps (flux IA routé par le même `request_id` que les composers, d'où les réducteurs atteints depuis `ui/events/compose.rs`) ; `tabs.rs` = la **barre d'onglets** du volet, toujours visible (chip « Sélection » = message choisi dans la liste, un clic dans la liste remet `active_tab = None` ; `MailboxState.open_tabs: Vec<ViewerTab>` mélange messages épinglés et composers inline — quand l'onglet actif est un composer, l'historique d'expéditeur est masqué, voir `inbox/mod.rs`) ; `cards.rs` = les **cartes repliables** autour du message affiché (`SentCard` + `CardBody` : réponses/transferts dont Aviary tient déjà le message, messages du fil chargés à la demande, et la liste plate de la conversation dessous) ; `reply.rs` = le **panneau de réponse** (`InlineReply` : un `ComposeView` sur la surface `Panel` plus les deux choses qui en font un panneau — le message dont il occupe le lecteur et la cible de réponse ; envoi, brouillons, IA, modèles, détachement et fenêtre d'annulation passent par les chemins ordinaires du composer, routés par `compose_id`) ; `quoted_body.rs` = découpe l'historique cité que les providers réinjectent dans chaque réponse (reconnaissance des conteneurs des clients courants, fragments rendus en sous-blocs repliables sans perdre le HTML d'origine confié à Blitz — réglage `collapse_quoted_messages`) ; `browser.rs` = aperçu et impression via le navigateur système (copie HTML autonome, images CID encodées hors du thread UI).
- `compose.rs` — the `ComposeView` entity, rendered on one of three surfaces (`ComposeSurface`) : **onglet du volet de lecture** (le mode par défaut d'un « Nouveau message » / contact / brouillon — `open_inline_compose` crée l'entité dans `AviaryApp.inline_composes` + un `ViewerTab::Compose(id)`; plusieurs rédactions coexistent, bandeau fermer / « Ouvrir dans une fenêtre » via `ComposeEvent`), **panneau de réponse** au-dessus du corps lu (`build_reply_panel_compose`, possédé par `viewer/reply.rs` : objet fixe affiché en titre au lieu d'un champ, corps plafonné) ou **fenêtre OS** (`open_compose_window`, utilisé pour le détachement). `build_hosted_compose` construit les deux surfaces hébergées par la fenêtre principale et les enregistre dans `composes`, si bien que le routage (`MailSent`, `DraftSaved`, flux IA, accusés de l'outbox), l'autosave de brouillon et la fenêtre d'annulation d'envoi (`PendingCancelEffect::Compose` → `restore_compose_surface`) sont les mêmes pour un onglet et pour le panneau ; seule la surface diffère (`hide_reply_panel`/`restore_reply_panel`/`discard_reply_panel`). Body is edited in the **block editor** (`block_editor.rs`); on send it runs `blocks::build_html_body` on `BlockEditor::to_blocks`; `body_is_html` is always true. `MailSent`/`DraftSaved` events are routed back through `AviaryApp.composes: Vec<ComposeHandle>` (`window: Option<WindowHandle>` — `None` pour l'inline — + weak entity keyed by `compose_id`). `composer_core.rs` holds `ComposerCore`, the composition state every `ComposeView` carries (recipient inputs, block editor, attachments, templates, `draft_id`, AI prompt input).
- `components/` — **Aviary-owned widgets**, not forks of gpui-component. `block_input.rs` (~1400 lines) is the multiline input every text block of the editor uses: it implements IME (`EntityInputHandler`), selection, clipboard, highlight runs, the correction/emoji completion menus and *visual*-line vertical navigation directly on gpui's public text primitives, borrowing only gpui-component's shared input actions and theme — so no private editor state has to be patched. `overlay_popover.rs` is its cursor-anchored popover. `display_map.rs` is what lets the input show something other than what it holds: an owner declares `FoldableRange`s (a link's brackets and destination, plus the extent that reveals them), and `DisplayMap` hides them from the string handed to the text system. Offsets then live in **two spaces** — *source*, spoken by the document, the caret, the clipboard and the IME, and *display*, spoken by the `TextLayout` — and every layout call site converts (`to_display` for the caret, the selection, the marked range and the highlight runs; `to_source` for hit-testing and vertical navigation). Folds are dropped unless their fingerprint matches the current value: the owner recomputes them one frame after an edit, and stale offsets would hide whatever now sits there. With nothing foldable the map is the identity and costs nothing. Note `block_editor.rs` imports them aliased (`BlockInputState as InputState`), so `InputState` inside the editor is *not* gpui-component's.
- `block_editor.rs` (+ `block_editor/{clipboard,emoji,history,input_actions,links,mentions,proofreading,remote_images,render,tables,toolbar}.rs`) — **éditeur WYSIWYG par blocs** (façon Notion) partagé par le composer (ses trois surfaces, panneau de réponse compris) et les éditeurs de signatures/modèles. Un `Entity<BlockInputState>` auto-grow par bloc textuel (paragraphe/titre/citation/code) ou par item de liste, stylé au rendu. Les touches structurantes (Entrée = scission, Retour arrière à l'offset 0 = fusion/dé-stylage, Tab = indentation de liste, ↑/↓ aux bords = bloc voisin) sont des **actions de l'input capturées sur un ancêtre** (`capture_action` + `cx.stop_propagation()` — la phase capture passe avant les handlers de l'input, voir `input_actions.rs`) ; les préfixes markdown (`# `, `- `, `> `, `---`, ``` ``` ```) transforment un paragraphe à la volée quand le curseur est juste derrière le préfixe (`BlockInputEvent::Change`). **Sélection multi-blocs** façon Notion : glisser au travers de plusieurs blocs (ou Maj+clic, ou Échap = bloc courant, ou Ctrl+A ×2) surligne des blocs entiers ; le conteneur prend alors le focus et son key context `BlockEditor` (bindings enregistrés par `block_editor::init` dans `ui::run`) route Ctrl+C/X (markdown vers le presse-papiers), Suppr/Retour arrière et Échap ; un collage multi-blocs dans un paragraphe re-scinde en vrais blocs (`markdown_to_blocks`). Le presse-papiers système ne transporte que le markdown : les images inline d'un copier/couper de blocs voyagent par l'annexe interne `CLIP_IMAGES` (réinjectées au collage si le texte collé correspond au dernier copier — y compris entre composers du même processus) ; l'aperçu du composer passe par `preview_markdown`, qui réécrit `cid:`/`bytes://cid-` vers le registre d'images. L'éditeur **possède les images inline** du brouillon (`images()`), rendues via `inline_images::register_bytes` : insertion par le bouton « Image » du composer / le menu de bloc (`prompt_insert_image*`, extensions filtrées par `image_mime_for_path`), collage d'une image bitmap du presse-papiers (`ClipboardEntry::Image`, supporté par gpui sous Wayland/X11), **poignée de redimensionnement** au survol (largeur mesurée au rendu par `on_children_prepainted` comme point de départ, `width` injecté dans le HTML sortant par `build_html_body`), et suppression d'un bloc image qui retire la pièce jointe devenue orpheline. **Les images d'un collage sont adoptées** (`remote_images.rs`) : un `<img src="https://…">` ou un `![](https://…)` collé partirait sinon en lien externe — cassé chez le destinataire dès que l'hôte exige un cookie ou disparaît, et signalant l'ouverture du courriel. Chaque source est donc réécrite en `cid:` sur une `InlineImage` du brouillon ; les charges `data:` (base64 seulement) sont décodées sur place, les distantes téléchargées par le runtime (`Cmd::FetchInlineImage` → `Evt::InlineImageFetched`, routé par `editor_id` = le `scope` de l'éditeur, comme les résultats LanguageTool). **Un octet manquant ne doit jamais partir** : l'URL d'origine de chaque cid en vol est conservée (`pending_remote_images`), un échec la rétablit dans le document et `build_outgoing` la remet dans le HTML sortant si l'envoi devance le téléchargement — une image inline vide ne s'afficherait pas du tout, là où le lien externe s'affiche au moins. Le parcours des blocs (`adopt_in_kinds`) et la réécriture des sources sont des fonctions libres, testables sans contexte gpui. **Annuler/rétablir au niveau document** : snapshots complets (`Snapshot` = kinds + images) empilés avant chaque opération structurelle (`push_undo`) et à chaque rafale de frappe (`note_text_change`, coalescence 1,2 s par input, état « d'avant » = `mirror` rafraîchi à chaque rendu) ; Ctrl+Z/Ctrl+Maj+Z passent par les actions locales de `BlockInput` et sont aussi bindés dans le contexte `BlockEditor` quand la sélection de blocs a le focus ; la restauration reconstruit les blocs et focalise le premier bloc modifié. **Navigation ↑/↓ inter-blocs** : l'action `MoveUp`/`MoveDown` est capturée puis vérifiée en différé (`cx.defer_in`) — l'input navigue en lignes *visuelles*, donc « en butée » se détecte par un curseur resté immobile ; le saut atteint aussi les blocs non textuels (image/séparateur/message d'origine) en les sélectionnant, et ↑/↓/Entrée déplacent/ouvrent la sélection ensuite. **Liens** (`links.rs`) : un lien est du markdown dans le texte du bloc — toujours `[libellé](url)`, même quand le libellé n'est que l'adresse répétée : `<url>` s'afficherait pareil une fois replié, mais son texte visible *est* sa destination, donc le renommer sur place casserait le lien. Rien de nouveau n'est persisté ni sérialisé, `build_html_body` produisant déjà l'`<a href>` (verrouillé par `both_link_forms_reach_the_outgoing_body_as_anchors`). Le libellé est coloré (`theme.link`) et souligné par `inline_format_highlights`, le reste estompé comme les autres marques. Le libellé porte `theme.link` dont la **luminosité est alignée sur celle du texte du corps** (`readable_link_color`, bornée à [0,35 ; 0,82] pour que la teinte survive à un texte quasi noir ou quasi blanc) : `primary` est choisi pour des boutons, posé sur un fond, et celui d'OneDark (0,66) est plus sombre que son propre texte (0,71), si bien qu'un lien non corrigé paraît éteint. La teinte et le soulignement suffisent à le distinguer. La destination porte `theme.muted_foreground` — une **couleur**, pas un `fade_out` : l'estompage mélange vers le fond, ce qui la rendait quasi invisible sur canevas sombre (luminosité ≈ 0,24 contre 0,18 pour le fond) et délavée sur blanc. Elle n'est de toute façon à l'écran que lorsque le lien est déplié, donc quand on la lit ou l'édite. Le libellé seul est affiché : les crochets et la destination sont **repliés** (`foldable_ranges` → `DisplayMap`, voir `components/`) et reviennent dès que le curseur ou la sélection touche le lien — y compris collé contre l'un de ses bords, sans quoi il serait inéditable. **Un bloc sans focus replie tout** : il conserve son caret là où il était, donc s'en remettre à la sélection laisserait le lien déplié après avoir quitté le bloc. **Ctrl+K** (bindé sur les contextes `BlockEditor` *et* `BlockInput`, l'action étant inconnue de l'input elle remonte sans capture) et le bouton « Lien » de la barre d'outils ouvrent un dialogue à deux champs : il **modifie le lien sous le curseur** s'il y en a un (bords inclus), sinon il habille la sélection ; une adresse vide dégrafe le lien en conservant son texte. Coller une URL nue la transforme en lien dans n'importe quel bloc textuel (item de liste compris), en habillant la sélection s'il y en a une. Les URL nues ne sont **pas** détectées dans le texte déjà saisi : pulldown-cmark implémente CommonMark, qui linkifie `<url>` mais pas `url`, si bien qu'un style appliqué sans les chevrons promettrait un lien que l'envoi n'aurait pas produit. **Complétions** : `emoji.rs` (deux-points en frontière de token, émoticônes texte, mots-clés FR/EN cachés) et `mentions.rs` (`@` → carnet d'adresses partagé, insère le nom affiché et ajoute le contact au champ À). **Bloc signature** : `BlockKind::Signature` (voir « Blocs » ci-dessous) est rendu comme un bloc opaque — le fragment tel que le destinataire le verra, par le même moteur Blitz qu'un corps reçu — sous un en-tête « Signature · <nom> » et un sélecteur listant les signatures du compte plus « Aucune » (`available_signatures`, poussé par le composer via `set_available_signatures` : à l'ouverture, au changement de compte d'envoi, et quand les Préférences en modifient une). Il n'est pas éditable en ligne : une signature s'édite dans **Préférences → Signatures**, ce qui fait de « changer de signature » un simple remplacement (`apply_signature` remplace le bloc **sur place** s'il y en a un, sinon insère au curseur comme un modèle) plutôt que la fusion de deux versions à moitié retouchées. Le composer offre le même sélecteur dans sa barre d'outils, à côté de « Modèles », pour un brouillon qui n'en a pas. Les images d'une signature abandonnée ne sont pas purgées : `build_outgoing` n'envoie déjà que ce que le corps référence, et les garder coûte quelques kilo-octets de brouillon contre le risque de perdre l'image d'une signature qu'on reprend. Entrée/sortie du document par `BlockKind` (`from_markdown`/`to_blocks`/`to_markdown`/`build_html`, `insert_kinds` pour les modèles).

- `snooze.rs` — **reporter un message à plus tard**. Une échéance est un état *côté Aviary* (`AccountSettings.snoozed_messages`), rangé à côté de l'épinglage et pour la même raison : aucun provider n'expose de report que les trois backends pourraient partager. **Le message ne bouge pas** — rien ne part au réseau au moment du report (donc rien à retenter, annuler ou réconcilier) et surtout **son identifiant ne change pas**, ce qu'un déplacement IMAP ne pourrait pas promettre (`UID MOVE` en émet un nouveau, le repli COPY+EXPUNGE n'en renvoie aucun). `filtered_message_headers` masque ce qui est reporté ; le filtre « Reportés » (`MailboxState.show_snoozed_only`, non persisté en session — c'est un mode de revue, pas une habitude) est **le seul endroit** où ces messages et leur échéance s'affichent. Le réveil est un **tick de 30 s** (`WAKE_TICK`, pompe de `AviaryApp::new`) plutôt qu'un minuteur armé sur la prochaine échéance : la seconde près n'a pas de sens ici et un tick n'a rien à ré-armer quand l'ensemble des échéances ou l'horloge bougent ; la première passe précède le premier tick, une échéance tombée application fermée étant déjà due au démarrage. Le réveil marque le message non lu (silencieux et par lot, comme la lecture d'un fil). **L'échéance remplace la date de réception sur la ligne** au lieu de s'y ajouter : les hauteurs sont indexées par `MsgEntryVariant` et un élément de plus dans cette colonne serait une variante visuelle que rien ne mesure. Les échéances prédéfinies sont des fonctions libres testées (une échéance passée disparaît du menu, « la semaine prochaine » un lundi ne veut pas dire ce matin, une date choisie veut dire *ce matin-là* et non le minuit qui l'ouvre).

**Expéditeurs bloqués** (`GlobalSettings.blocked_senders`) : le courrier de ces adresses est déplacé vers les indésirables à l'arrivée, dans `events/mailbox.rs::on_new_messages` — **avant** les notifications de bureau et avant le filtre de pertinence par compte, un expéditeur bloqué ne devant ni sonner ni dépendre du compte affiché. - `blitz_body.rs` (+ `blitz_body/{actor,bands,element,events,net,outlook,paint,selection,theme,tests}.rs` — le fichier parent ne garde que l'état partagé : `Entry`, le `BlitzCache` qui le contient, les clés de cache, le `Job` d'un rendu préparé et les types qui traversent la frontière de thread ; `element.rs` = élément gpui, points d'entrée, liens et zoom, `bands.rs` = quelles bandes rasteriser et quand + les deux pompes, `events.rs` = souris/clavier et copie de sélection, `actor.rs` = le thread du document, `paint.rs` = mise en page et rasterisation sur ce thread) — mode **« Fidèle »** du lecteur (`BodyViewMode::Blitz`, le défaut) : le HTML d'origine est rendu par le moteur **Blitz** (Stylo + Taffy + parley, crates `blitz-{dom,html,paint,traits}` 0.3.0-beta), rasterisé en CPU (`anyrender_vello_cpu`) puis affiché comme image (`RenderImage`, RGBA→BGRA, découpe en tuiles/bandes de 2048 px pour les limites de texture). La rasterisation est **paresseuse, pilotée par le viewport** : seules les bandes autour de la zone visible (origine de la sonde vs viewport fenêtre) sont peintes au rendu initial ; les bandes manquantes sont demandées à l'acteur par une pompe dédiée (`pending_bands`/`pump_bands`, `DocCmd::PaintBands`) au fil du défilement, les bandes loin hors écran sont évincées, et les tuiles non peintes sont des placeholders à hauteur connue. La préparation UI (réparations Outlook de `outlook.rs`, clé de cache, images) est **mémoïsée par emplacement** (`PrepCache`) car `element()` tourne à chaque frame ; le `FontContext` Blitz est un prototype partagé cloné par document (scan des polices système fait une seule fois, `SourceCache` partagé). Le document reste **vivant et interactif** : `HtmlDocument` n'est pas `Send`, donc chaque rendu vit sur son **thread acteur** (`spawn_doc_thread` — rend, envoie `Rendered` + `LiveDoc{tx}` par oneshot, puis boucle sur les `DocCmd` ; la fermeture du canal à l'éviction termine le thread). Les événements souris gpui sont convertis en `UiEvent` Blitz (coordonnées = position − origine mémorisée au prepaint, en px logiques) et poussés dans `Entry.pending` ; une **pompe** (une par entrée, `pump_running`) les envoie par lots au thread acteur et applique le retour : curseur (`get_cursor` → I-beam/main), re-rasterisation seulement si une sélection est **visible** avant/après le lot (un clic simple — lien, zone vide — ne repeint rien) et seulement pour les **tuiles intersectant la zone touchée** (`PaintState` suit le trajet du pointeur + l'étendue de la sélection ; `paint_tile_band` rend une bande en réglant `set_viewport_scroll` — le painter culle le reste ; marge `DIRTY_MARGIN_CSS`, repli « toutes les bandes matérialisées » si la zone est inconnue). vello_cpu tourne avec la feature `multithreading` (rayon). Le survol ne coûte qu'un hit-test. On obtient ainsi la **sélection de texte** (surlignage peint par le moteur, Ctrl+C copie via `selection.rs` — texte + fragment HTML + images vers `rich_clipboard` —, Échap efface, focus clavier par `track_focus` + clic) et les **liens cliquables** (clic d'ancre → `NavigationProvider` de `net.rs` (`OpenLinks`) → `open::that_detached`, schémas http/https/mailto seulement). Re-rendu (sélection perdue) quand la largeur mesurée change (`on_children_prepainted`), cache global `BlitzCache` (LRU 6 entrées + budget mémoire de tuiles 256 Mo, clé = message + hash du corps + « images distantes »). **Un document vivant coûte bien plus que ses tuiles** (~20 Mo mesurés — arbre stylé Stylo, layout Taffy, texte façonné parley, images décodées — contre ~5 Mo de tuiles) et le budget d'éviction ne le voit pas, puisqu'il ne compte que les pixels. `sweep_idle_documents` (appelé depuis `element()`, au plus une fois par seconde) libère donc le `LiveDoc` de toute entrée absente de l'écran depuis `DOCUMENT_IDLE_TIMEOUT` : le canal se ferme, le thread acteur rend la main et le document part avec lui, **mais les tuiles restent** — revenir au message le réaffiche instantanément pendant qu'un document est reconstruit. `last_target`/`live_target` sont remis à `None` avec, sinon `request_target` croirait l'entrée à jour et ne reconstruirait jamais le document, laissant en placeholders définitifs les bandes non encore rasterisées. Ressources via le `NetProvider` maison de `net.rs` : `cid:` depuis `Message.inline_images`, `data:` décodées localement, `http(s)` seulement si « images distantes » est actif — la requête part sur le runtime tokio de l'app via `runtime::TOKIO_HANDLE`. **Le premier rendu n'attend pas le réseau** : `NetPending` sépare les ressources livrées immédiatement (`cid:`, `data:`, distantes bloquées — appliquées avant la première peinture, sinon les images inline manqueraient à la première frame) des ressources distantes en vol ; la boucle `resolve` initiale ne bloque que sur les premières et sur les ressources critiques de Blitz (`has_pending_critical_resources`, les feuilles de style de `<head>`, qui décident la mise en page). Un pixel de tracking sur un hôte injoignable retenait sinon tout le corps pendant les 7 s de son timeout HTTP. Les images arrivées ensuite sont réappliquées par la **pompe de ressources** (`pump_resources`, armée au prepaint comme celle des bandes, sondage 200 ms, budget 10 s) : `DocCmd::ApplyResources` draine les livraisons côté acteur, re-`resolve` et re-rasterise (`apply_resources_doc` — la hauteur change souvent, l'image n'ayant pas de taille intrinsèque au premier passage), et `Rendered.resources_pending` dit à la pompe quand s'arrêter. La sélection de texte est perdue à ce repaint, comme à tout repaint complet. Le garde-fou global reste `NET_TIMEOUT` (8 s). `theme.rs` fournit les feuilles UA, force éventuellement Inter / `body_font_size` (`force_uniform_font_family`, `force_uniform_font_size`) et **adapte les couleurs neutres en mode sombre** ; `force_light_email_preview` garde au contraire une toile blanche façon navigateur même quand l'application est sombre. Tests : `cargo test blitz_body` (rendu, sélection par glisser, clic de lien, data-URI).
- `settings.rs` — persisted `Settings`/`GlobalSettings`/`AccountSettings`, stored as pretty JSON at `~/.config/aviary/settings.json`. La session (`AppSession`) est un fichier séparé, `session.json` (compact, écriture atomique 0600), chargé par `AppSession::load()` dans `AviaryApp::new`.

Les instantanés `sent_messages` sont plafonnés à 50 à la persistance. Les octets binaires (`InlineImage.bytes`, `Attachment.bytes`) sont sérialisés en **base64** (`model::b64_bytes`) — partout, cache SQLite compris.
- `theme.rs` — light/dark via `Theme::change` + the OneDark palette applied onto `ThemeColor` fields; presets and the custom palette keep separate light/dark variants so switching mode never loses the user's edits.
- `icons.rs` — icons are **lucide SVG files** under `assets/icons/`, embedded via `rust-embed` and served through the `AssetSource` in `ui/mod.rs` (gpui-component resolves its own `IconName`s against the same folder). `icons::app_icon("mail")` loads `icons/mail.svg`.
- `util.rs` / `datefmt.rs` — pure helpers (address parsing, account colors, localized dates).

gpui conventions used throughout: state that outlives a frame lives in `Entity<T>` (e.g. every text field is an `Entity<InputState>` created once and kept on the struct — never recreate them in `render`); `cx.listener(...)` for handlers that mutate the view; `cx.subscribe_in` for `InputEvent`s (subscribe **once**, in the constructor, never in `render`); toasts via `window.push_notification(...)` (requires the `Root` wrapper, whose notification/dialog/sheet layers are re-emitted at the end of `AviaryApp::render`).

### Fenêtres secondaires

Le composer s'ouvre **par défaut dans le volet de lecture** (voir `compose.rs` ci-dessus) ; les fenêtres OS (`cx.open_window` + `Root`) servent au détachement, aux composers supplémentaires et aux événements calendrier. Handles (`Option<WindowHandle<Root>>` + `WeakEntity<view>`) are kept on `AviaryApp` so `handle_event` can route runtime replies (`MailSent { compose_id }`, `EventCreated { request_id }`) to the right compose and close it (`window.remove_window()` / libération du volet). Message previews and replies stay **inside** the main window (tabs + inline reply, see `viewer/` above) — no OS windows for those.

### Auth

`auth/microsoft.rs` implements the Microsoft device-code flow against `login.microsoftonline.com/{tenant}`. The scope string is hardcoded (`SCOPE` constant) and includes `offline_access Mail.ReadWrite Mail.Send Calendars.ReadWrite People.Read User.Read`. If you add a Graph endpoint that needs a new scope, update `SCOPE` and the user will need to re-auth — the same holds for `auth/google.rs`'s `SCOPE` (`gmail.modify`, `gmail.send`, `calendar.events`, `contacts.readonly`, …).

`auth/google.rs` implements Google's OAuth 2.0 installed-app flow with **PKCE + loopback redirect**. `auth/imap.rs` stores the IMAP/SMTP password in the OS keyring and the server config in the per-account token file.

The unified `Tokens` struct stores `provider: Provider`, the issuing `client_id`, and `tenant` (Microsoft-only). Each account stores its provider on `BgAccount` and `BgAccount::ensure_auth` dispatches refresh via `match self.provider`. `Cmd::StartLogin` is Microsoft-only; `Cmd::StartGoogleLogin` / `Cmd::StartImapLogin` trigger the other flows.

### Provider abstraction (`src/providers/`)

`providers/mod.rs` exposes the unified API surface as methods on **`Session<'a>`** — an enum `{ Graph { client, token, tenant }, Gmail { client, token }, Imap(ImapAuth) }` pairing a backend with its live credentials, so a provider/credentials mismatch is unrepresentable. Runtime tasks build one per call: `let Some(auth) = account.auth_or_report().await else { return }; account.session(&auth).list_folders().await` (`auth_or_report` = `ensure_auth` + the standard `Evt::Error` reporting; tasks that emit a specific error event — send, event create — call `ensure_auth` directly). During login, before a `BgAccount` exists, `auth_flow.rs` constructs the `Session` inline. Runtime modules only call the `Session` surface; **never** call `providers::graph::*` / `gmail::*` / `imap::*` directly from runtime code or the UI. The shared `OutgoingMessage` / `NewCalendarEvent` borrow types live in `providers/mod.rs`, and `providers/error.rs` normalizes backend failures into translated messages.

**Move aliases** (`ARCHIVE_FOLDER_ALIAS` = `archive`, `JUNK_FOLDER_ALIAS` = `junkemail`, `INBOX_FOLDER_ALIAS` = `inbox`) let one UI call site work across the three providers: Graph treats them as well-known folders, Gmail translates them into label mutations (archiving = dropping `INBOX`, since it has no Archive label), and IMAP resolves them against the account's own folder list (`well_known_move_alias`) because it infers well-known names from `LIST` attributes rather than being told them — failing with a translated error when the server has no such mailbox. The UI passes the account's real folder id when it knows it (`AviaryApp::well_known_folder_id`) and the alias otherwise. **Junking a message reports no source folder**, exactly like archiving: Graph and IMAP ignore it, but for Gmail the source is the label to *remove*, and passing the folder on screen would strip that label while leaving the message in the inbox — flagged as spam yet still delivered. « Non indésirable » is the one action that does report a source, since Gmail needs `SPAM` dropped explicitly. Both are locked by tests in `gmail/messages.rs`.

### Microsoft Graph (`providers/graph/`)

`providers/graph/*.rs` is the *only* place that should know about Graph JSON shapes. Pagination uses Graph's `@odata.nextLink` — `fetch_messages_page` follows those links.

Incoming HTML mail is converted to Markdown via `html_to_markdown_rs::convert(html, Some(html_md_options()))` (`providers/html.rs`). The options set `extract_metadata: false` and `exclude_selectors: ["head", "meta", "title", "link", "style", "script"]` — this is what prevents the Outlook CSS preamble and Word/Apple meta tags from leaking into the rendered body. Keep that selector list when adjusting the helper. Inline `cid:` references in the converted markdown are rewritten to `bytes://cid-{cid}`; le mode Markdown les rétablit en `cid:` avant de les confier au `NetProvider` Blitz avec les `Message.inline_images`.

### Gmail / Google (`providers/gmail/`) et IMAP (`providers/imap/`)

Mirror `providers/graph/` 1:1 in API surface but map each protocol's idioms to Aviary's domain types (labels ⇔ folders, `UNREAD`/`STARRED` labels ⇔ read/flag state, `threadId` ⇔ `conversation_id`, opaque `nextLink` blobs for pagination, RFC 822 assembly for send, soft-delete via trash). See the module docs in each backend for details. **IMAP has no conversation id**, so `derived_conversation_id` synthesises one: the thread's *root* `Message-ID`, which RFC 5322 puts first in `References` (falling back to `In-Reply-To`, then the message's own id). It is computable from one message's own headers, so every page of a listing agrees without shared state — deliberately with no fallback on the normalized subject, which would merge unrelated "Re: contrat" exchanges. `list_thread` rebuilds a thread by SEARCH-ing the inbox and Sent only, since it runs on every message open. IMAP uses the **sync** `imap` crate wrapped in `spawn_blocking` (one-shot connect → login → op → logout per call), `lettre` for SMTP and `mail-parser` for the RFC822 bytes returned by FETCH.

### Blocs (`src/blocks/`)

`Block`/`BlockKind` document model (used by `model::Signature`/`Template` persistence and edited directly by `ui/block_editor.rs`) and the markdown/HTML serialization (`markdown_to_blocks`, `blocks_to_markdown`, `build_html_body`). `build_html_body` is the single producer of outgoing HTML — compose, event descriptions and signatures all go through it.

**`BlockKind::Signature` est le bloc de la signature insérée dans un brouillon**, distinct de `RawHtml` (fragment collé ou importé) : il porte l'identifiant de la signature, son nom au moment de l'insertion et son **HTML rendu une fois pour toutes** (`compose::signature_block_kind` → `build_html_body` sur ses blocs). Elle était auparavant *dissoute* dans le document — ses blocs versés parmi ceux de l'utilisateur —, si bien que rien ne disait où elle commençait ni finissait : on ne pouvait ni la nommer, ni la remplacer, et une signature HTML importée s'affichait en « fragment HTML » anonyme. Le HTML est figé à l'insertion pour la même raison que celui d'`OriginalMessage` : un brouillon ne doit pas changer parce que la signature a été modifiée dans les Préférences depuis. À la sérialisation, le bloc émet le marqueur `<div data-aviary-signature="{id}">` que `build_html_body` remplace par le fragment, enveloppé dans `<div class="aviary-signature" data-aviary-signature-id="{signature_id}">` — la classe que les autres clients posent aussi, pour que le destinataire (et Aviary relisant son propre courrier) distingue la signature du message. **Seul l'identifiant voyage**, pas le nom : c'est la formulation de l'utilisateur, et le composer la retrouve dans les réglages du compte (`compose::name_signature_blocks`).

**`html.rs` est le chemin de retour** : un brouillon enregistré chez le provider revient en HTML, et `html_to_blocks` reconstruit le document en parcourant le DOM (`scraper`) plutôt qu'en passant par la conversion Markdown du lecteur. Celle-ci est faite pour *lire* du courrier — elle déplie les tableaux de mise en page, jette les classes qu'Aviary pose sur ses propres structures et réécrit les `cid:` en `bytes://` — donc un brouillon écrit ici en revenait en suite de paragraphes, signature dissoute et citation aplatie. Deux règles : **ce que l'éditeur sait tenir devient un vrai bloc** (titres, listes imbriquées, citations, code, tableaux, séparateurs, images inline avec leur largeur ; marques réécrites en Markdown, y compris quand le client d'origine les exprime en CSS sur un `<span>`, ce que font Outlook et Gmail) et **ce qu'il ne sait pas tenir reste opaque au lieu d'être aplati** (`Signature`, `OriginalMessage`, `RawHtml` pour un tableau dont les cellules ont leur propre structure ; un tableau à cellule unique est au contraire une contrainte de largeur et son contenu ressort en blocs). Sont reconnues les conventions d'Aviary d'abord, puis celles qu'un brouillon écrit ailleurs peut porter : `gmail_signature`/`gmail_quote`, et le `<div id="divRplyFwdMsg">` d'Outlook Web — qui n'enveloppe pas ce qu'il cite mais le laisse en *frères*, d'où la règle « tout ce qui suit est la citation ». Le texte est importé tel quel, sans échappement Markdown : l'éditeur affiche sa propre syntaxe, un `\` visible devant chaque `*` serait pire que le risque. `saving_a_reopened_draft_produces_the_same_html_again` verrouille l'idempotence — un brouillon repris chaque jour ne doit pas s'emboîter d'un niveau à chaque enregistrement.

### Assistant IA (`src/ai.rs`, `runtime/ai.rs`)

`ai.rs` holds only serializable data (settings + `AiPromptPreset` templates whose variables are `[[instruction]]`, `[[instruction_optional]]`, `[[subject]]`, `[[body]]`); every HTTP call lives in `runtime/ai.rs`. Four providers — OpenAI, Anthropic, Gemini and an OpenAI-compatible `Local` base URL — are normalized into a **single SSE stream**, whose small fragments are coalesced to a frame-sized cadence before crossing into gpui. Results are routed back to the originating composer by `compose_id`, like sends.

### Correction (`ui/spellcheck.rs`, `src/proofreading.rs`, `runtime/languagetool.rs`)

Two independent layers, both optional and both surfaced in **Préférences → Correction**:

- **Offline spelling** — always local, `spellbook` + the embedded Hunspell FR/EN dictionaries (see `ui/spellcheck.rs` above).
- **LanguageTool grammar** — `LanguageToolMode` is `Disabled`, `LocalManaged` (Aviary downloads and runs the Java distribution itself; `runtime/languagetool.rs` owns the child process, the download, archive extraction and Java discovery through `JAVA_HOME`/`PATH`/platform paths) or `ExternalUrl`. The UI only sends commands, so nothing ever blocks gpui's foreground thread. `LanguageToolCoverage` decides whether it also replaces the local speller.

Issues come back as `ProofreadingIssue` ranges and are painted as highlight runs by `BlockInput`, with the fix menu on right click.

### Linux-only bits

`tray.rs` (system tray via `ksni`) is gated by `#[cfg(target_os = "linux")]`. The tray runs on its own thread and feeds `TrayAction`s back through an mpsc channel drained by a gpui foreground task (`AviaryApp::handle_tray`). Notifications (`notify.rs`, via `notify-rust`) work everywhere.

`ksni` is declared with `default-features = false, features = ["blocking", "async-io"]`. **Do not** re-enable the `tokio` feature: it would set `zbus/tokio` and — via Cargo feature unification — flip every other zbus consumer into tokio mode, which panics from threads without a runtime entered. The spawn pattern is `use ksni::blocking::TrayMethods; tray.spawn()`.

### gpui / gpui-component — pièges connus

- gpui renders through **blade (Vulkan)** on Linux: `shell.nix` must keep `vulkan-loader` in `LD_LIBRARY_PATH` (plus wayland/x11/fontconfig/freetype).
- All SVG icons referenced by gpui-component's `IconName` must exist in `assets/icons/` (embedded by the `Assets` struct in `ui/mod.rs`); missing files log render errors. When using a new built-in component, check which `IconName`s it draws.
- **Les runs de highlight doivent être triés et disjoints.** `StyledText::with_highlights` délègue à `compute_runs`, qui parcourt les plages *dans l'ordre donné* et convertit chacune en **longueur** de run consécutive : une plage non triée fait régresser son curseur interne et décale tout ce qui suit (symptôme : le texte après un lien se colore). Deux plages qui se chevauchent produisent le même effet. Or `inline_format_highlights` émet naturellement (contenu, délimiteur gauche, délimiteur droit) — non trié — et la correction orthographique peut recouvrir une marque inline. Tout doit donc passer par `combine_highlights`, qui trie les endpoints et fusionne les styles superposés. Un délimiteur **symétrique** (`**gras**`) retombe juste par coïncidence de longueurs, ce qui a masqué le problème jusqu'aux liens (`[` d'un côté, `](url)` de l'autre). Verrouillé par `combined_highlights_are_sorted_and_disjoint`.
- `Theme::change(mode, …)` resets colors from the registry; apply palette overrides (OneDark) **after** it, then `cx.refresh_windows()` (see `ui/theme.rs::apply`).
- `cx.theme()` borrows `cx`; when a render closure later needs `&mut cx`, clone the theme first (`let theme = cx.theme().clone();`).
- `TextView::markdown/html` need `(window, cx)` and parse asynchronously; `.scrollable(true)` requires a fixed-height parent.
- Fonts: Inter / JetBrains Mono / NotoEmoji are embedded and registered in `ui::install_fonts`; `theme.font_family = "Inter"`.
- Editor text inputs are Aviary's `components::block_input`, not gpui-component's `InputState` — extend that component rather than patching gpui-component.
- **Cohabitation gpui + Blitz/Stylo** (deux pièges d'unification de features) : (1) gpui active `log/kv_serde`, ce qui met `serde_fmt` dans le graphe et son `impl From<serde_fmt::Error> for fmt::Error` rend ambigu le `?` des impls générées par `derive(ToCss)` de Stylo → `stylo_derive` est **vendorisé et patché** dans `patches/stylo_derive/` (`?` remplacés par des `match` explicites). (2) gpui active `yeslogic-fontconfig-sys/dlopen` (via font-kit) → la dépendance directe `fontique` avec la feature `fontconfig-dlopen` aligne fontique (tiré par blitz-dom/parley) sur cette API, sinon ses imports fontconfig échouent à la compilation.
- **`patches/`** holds four crates pinned through `[patch.crates-io]` — `blitz-dom`, `blitz-paint`, `cosmic-text`, `stylo_derive`. They are minimal buildable copies of upstream, **not forks to develop in**: `patches/README.md` lists the exact versions, the six modified files and the update procedure (re-copy the new crates.io sources, re-apply only those changes, never just bump the version number).
- Dev builds compile the rendering hot path (Blitz, Stylo, taffy, parley, vello_cpu, gpui, image) at `opt-level = 3` while application code stays at 1 — see the `[profile.dev.package.*]` block in `Cargo.toml` before "fixing" a slow debug build.
