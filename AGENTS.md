# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Privacy and test data

Never copy user-provided or real-world sensitive data into source code, tests, fixtures, snapshots, logs, comments, examples, documentation, or commit messages. This includes personal names, email addresses, phone numbers, physical addresses, account or tenant identifiers, message contents, company or client names, domains, URLs, and credentials.

Use unmistakably synthetic, role-based placeholders (for example, `Contact A` or `Organisation de test`) and reserved domains such as `example.com`, `example.test`, and `example.invalid`. Before keeping a fixture derived from an email, screenshot, bug report, or conversation, reduce it to the minimum structure required by the test and anonymize every identifying value. Never reuse details supplied by a user, even when those details appear to be public.

## Commands

All commands go through `nix-shell` via the `justfile`. Avoid `cargo` directly unless you have the runtime libs from `shell.nix` already in scope.

- `just` / `just run` — debug build, runs the app
- `just release` — `cargo run --release`
- `just check` / `just clippy` (`-D warnings`) / `just fmt`
- `just build` — release binary
- `just logout` — wipe pending and per-account credentials to force re-auth

There is no test suite. Linting = `just clippy` and the project must always pass with `-D warnings`.

The Azure AD app `client_id` + `tenant` are bundled as `auth::DEFAULT_CLIENT_ID` and `auth::DEFAULT_TENANT` constants. The default registration is multi-tenant + public client; users in restrictive tenants can override either value via **Préférences → Comptes → Configuration Azure (avancé)**, persisted in `settings.json` as `Settings.global.azure_client_id` / `azure_tenant` (empty string ⇒ use default). The effective values are passed in with `Cmd::StartLogin { client_id, tenant }` and persisted onto the issued `Tokens` so each account refreshes against the registration it was authenticated with, even if the override is changed later.

`auth::DEFAULT_GOOGLE_CLIENT_ID` / `DEFAULT_GOOGLE_CLIENT_SECRET` are the Gmail equivalent — a "Desktop app" registration. Contrary to what this file said before: Google's installed-app flow **does** require the secret in the code exchange, PKCE notwithstanding (PKCE is what makes holding it safe, per RFC 8252's "native apps are public clients"). **Both are injected at build time** through `option_env!("AVIARY_GOOGLE_CLIENT_ID"/"AVIARY_GOOGLE_CLIENT_SECRET")` instead of living in the sources, the secret falling back to an empty string. The point is not confidentiality — a shipped binary yields it to `strings` — but keeping a `GOCSPX-…` literal out of a public repository, where secret scanners get it revoked and every signed-in Gmail account breaks at its next refresh. `.github/workflows/release.yml` provides it from repository secrets; a plain `cargo build` gets none.

Users provide their own registration via **Préférences → Comptes → Configuration Google** (`Settings.global.google_client_id` / `google_client_secret`), which is the path for any build without a bundled secret; `AviaryApp::start_google_login` demands both halves before dispatching, so a half-configured client fails with Aviary's message rather than Google's. Note also that `gmail.modify` is a *restricted* scope: without Google OAuth verification the bundled registration is capped at 100 test users.

The UI supports **French and English** through `rust-i18n` (`assets/i18n/fr.json` and `en.json`). All user-visible labels, buttons, status messages, provider errors, placeholders, and generated reply/forward text must use `tr!`; never hardcode UI copy. Keep both catalogs key- and placeholder-compatible (covered by `ui::i18n_tests`) and use rust-i18n's `%{name}` placeholder syntax in the catalogs. **Préférences → Apparence → Langue** applies the language immediately to every open window and persists `Settings.global.language`; `Système` resolves through `sys-locale` with environment-variable fallback.

## Architecture

Desktop email/calendar/kanban client supporting **Microsoft 365** (Graph API + device-code OAuth), **Gmail** (Gmail/Calendar/People APIs + PKCE loopback OAuth) and **IMAP/SMTP**, built on **gpui 0.2** (Zed's UI framework) + **gpui-component 0.5** (widgets: inputs, resizable panels, menus, dialogs, notifications, markdown/html `TextView`, theming). The providers are abstracted behind a `Provider` enum (`crate::model::Provider`); every backend call dispatches through `providers::*` (see "Provider abstraction" below).

### Two-thread Cmd/Evt loop

The single most important pattern: the UI never does I/O. `runtime::spawn` starts a dedicated OS thread hosting a current-thread Tokio runtime, and the UI talks to it through unbounded mpsc channels:

- UI → background: `runtime::Cmd` (StartLogin, Refresh, OpenMessage, SendMail, LoadCalendar, LoadContacts, LoadSenderHistory, …)
- background → UI: `runtime::Evt` (DeviceCode, Authenticated, Messages, MessageOpened, Thread, Contacts, MailSent, Error, …)

`AviaryApp::new` spawns a foreground task (`cx.spawn_in`) that `await`s `evt_rx.recv()` and calls `handle_event(evt, window, cx)` + `cx.notify()` for each event. **When you add a new async operation, follow this pattern**: define a `Cmd` variant, dispatch it via `tokio::spawn` in `runtime::run`, and emit `Evt`s back — never block the UI thread, never call `reqwest` from the UI side.

`BgAccount::ensure_auth` transparently refreshes the OAuth access token (30-second grace window) before any provider call. New background functions should always call it (usually via `auth_or_report`) instead of touching `state.tokens` directly.

Runtime layout: `runtime/protocol.rs` holds the pure data protocol — `Cmd`, `Evt`, and the composite payloads `OutgoingMail` (SendMail/SaveDraft) and `EventDraft` (CreateEvent), each with a borrowed view (`as_outgoing`/`as_new_event`) toward the provider types. `runtime/mod.rs` keeps `spawn`, `BgGlobal`/`BgAccount` and the `run()` dispatch loop (`BgGlobal::spawn_on` resolves the account and spawns the task); the per-domain tasks live in `mailbox.rs`, `send.rs`, `calendar.rs`, `contacts.rs`, `sender_history.rs`, `auth_flow.rs`, `accounts.rs`. `mail_cache.rs` owns SQLite on a dedicated actor thread; message metadata is JSON but inline images and attachment bytes are normalized into `BLOB` tables.

### UI module layout (`src/ui/`)

`AviaryApp` (in `ui/app.rs`) is the root gpui `Entity` holding all UI state. Each view adds its render methods in its own file via `impl AviaryApp` blocks:

- `app.rs` — the `AviaryApp` struct, its construction (event/tray pumps, input subscriptions), command helpers (`send`, `send_refresh`, `switch_to_account`, `select_folder`, `open_message`, …) and the window chrome (topbar `TitleBar` + `TabBar` Courrier / Calendrier / Kanban / Contacts / Préférences, account switcher, `Render` impl re-emitting the `Root` layers).
- `state.rs` — pure UI state types: `AuthState`, `MainView`, `ThreadBodyState`, `MailboxState` (including `open_tabs`/`active_tab` for the viewer tabs; `ViewerTab::Loading(MessageRef)` represents a session reference being restored from SQLite), `SenderHistoryState`, `ContactsState`.
- `events.rs` — the receiving half of the Cmd/Evt pair: `handle_event` (every `Evt`, with the per-account relevance filter and `event_account_id`) and `handle_tray`.
- `app/undo.rs` + `events/outbox.rs` — les mutations annulables et les accusés de l'outbox. Une action groupée soumet une opération par message, donc une réponse par message : `BulkCompletions` (`ui/app.rs`) les agrège en une seule issue — succès et échecs comptés, première erreur du provider retenue, un seul toast (tout passe / rien ne passe / partiel). Un lot est enregistré **au moment où ses commandes partent** (dans `schedule_action`) et sa composition est déduite des commandes elles-mêmes : une action annulée pendant sa fenêtre n'envoie rien, donc n'a pas de lot à nettoyer. L'agrégation expire après `BULK_COMPLETION_TTL` (20 min, garde-fou mémoire dimensionné au-dessus des ~10 min de backoff de l'outbox). Un lot ne signale qu'un seul différé et ne recharge dossiers et listing qu'une fois, à sa dernière réponse.
- `auth_view.rs` — login screens (device code, Google redirect, IMAP form).
- `inbox/` — 3-pane mail view built with `h_resizable`/`v_resizable`. `mod.rs` = the panes container + sender-history pane; `folders.rs` = single-account list or unified per-account tree, context menus, create/rename/delete dialogs; `message_menu.rs` = les menus d'une ligne de message : le menu contextuel (clic droit) et le sous-menu « déplacer » partagé avec la barre groupée (`MoveScope` : même hiérarchie de dossiers pour un message et pour une sélection, seule l'action feuille diffère). `messages.rs` = search input + `message_row` (reused by sender history and the Contacts view) + "Charger plus". La liste est **virtualisée** (`v_virtual_list`) : sections → lignes aplaties en `MsgEntry`, hauteurs mesurées hors écran par variante (`MsgEntryVariant`, dérivée des champs sur lesquels le rendu branche — une différence visuelle absente de la clé décale toute la liste). Elle est aussi **regroupée par conversation** (`group_by_conversation`, activé par défaut ; recherche à plat) : `group_message_items` replie sur `(account_id, conversation_id)`, un fil prend la place de son message le plus récent, un fil d'un seul message chargé reste une ligne ordinaire. La ligne de groupe est ce message le plus récent (même `message_row_inner`), avec chevron de dépli et pastille de compteur ; sélection et épinglage portent sur le fil, et **son menu contextuel agit sur le fil** quand elle est repliée (supprimer, archiver, déplacer, lu/non lu, épingler ; ouvrir, répondre, transférer, actions rapides et **étiquettes** restent sur le message — une étiquette alimente le Kanban). Ouvrir une ligne repliée **marque lus ses membres chargés** (`collapsed_conversation_members` + `mark_conversation_read`) : la ligne porte la marque de non-lu du fil. Ce marquage vit dans `open_message` et dans le différé de `open_message_debounced`, pas dans le clic — j/k ne doit pas lire les fils qu'il survole.
- `viewer/` — the reader pane. `mod.rs` = body rendering (Fidèle/Markdown/Source — Fidèle est le défaut ; Fidèle rend le HTML original via `blitz_body.rs`, Markdown convertit le corps normalisé en HTML puis utilise le même moteur interactif, Source utilise le `TextView` public de gpui-component), tag bar, attachments, conversation thread (lazy `LoadThreadMessage`), and `request_message_tab` (deferred open used by the kanban double-click) ; `header.rs` = tout ce qui est au-dessus du corps (objet, actions, adresses, contrôles d'affichage, étiquettes ; `ViewerChrome` porte les deux largeurs sous lesquelles l'en-tête reflue) ; `attachments_panel.rs` = le panneau de pièces jointes et ses récupérations ; `translation.rs` = la traduction éphémère du corps ; `tabs.rs` = la **barre d'onglets** du volet, toujours visible (chip « Sélection » = message choisi dans la liste, un clic dans la liste remet `active_tab = None` ; `MailboxState.open_tabs: Vec<ViewerTab>` mélange messages épinglés et composers inline — quand l'onglet actif est un composer, l'historique d'expéditeur est masqué, voir `inbox/mod.rs`) ; `cards.rs` = les **cartes repliables** autour du message affiché (`SentCard` + `CardBody` : réponses/transferts dont Aviary tient déjà le message, messages du fil chargés à la demande, et la liste plate de la conversation dessous) ; `reply.rs` = le **panneau de réponse** (`InlineReply` : un `ComposeView` sur la surface `Panel` plus les deux choses qui en font un panneau — le message dont il occupe le lecteur et la cible de réponse ; envoi, brouillons, IA, modèles, détachement et fenêtre d'annulation passent par les chemins ordinaires du composer, routés par `compose_id`).
- `block_editor.rs` — éditeur WYSIWYG par blocs partagé par le composer et les éditeurs de signatures/modèles. **`BlockKind::Signature`** est le bloc de la signature d'un brouillon (identifiant + nom + HTML rendu une fois à l'insertion), distinct du `RawHtml` d'un fragment collé : dissoute dans le document comme avant, la signature n'était ni nommable ni remplaçable. Rendu opaque par Blitz sous un en-tête « Signature · <nom> » et un sélecteur (`set_available_signatures`, poussé par le composer) ; `build_html_body` la réinjecte dans `<div class="aviary-signature">`.
- `compose.rs` — the `ComposeView` entity, rendered on one of three surfaces (`ComposeSurface`) : **onglet du volet de lecture** (le mode par défaut d'un « Nouveau message » / contact / brouillon — `open_inline_compose` crée l'entité dans `AviaryApp.inline_composes` + un `ViewerTab::Compose(id)`; plusieurs rédactions coexistent, bandeau fermer / « Ouvrir dans une fenêtre » via `ComposeEvent`), **panneau de réponse** au-dessus du corps lu (`build_reply_panel_compose`, possédé par `viewer/reply.rs` : objet fixe affiché en titre au lieu d'un champ, corps plafonné) ou **fenêtre OS** (`open_compose_window`, utilisé pour le détachement). `build_hosted_compose` construit les deux surfaces hébergées par la fenêtre principale et les enregistre dans `composes`, si bien que le routage (`MailSent`, `DraftSaved`, flux IA, accusés de l'outbox), l'autosave de brouillon et la fenêtre d'annulation d'envoi (`PendingCancelEffect::Compose` → `restore_compose_surface`) sont les mêmes pour un onglet et pour le panneau ; seule la surface diffère (`hide_reply_panel`/`restore_reply_panel`/`discard_reply_panel`). Body is edited in the **block editor** (`block_editor.rs`); on send it runs `blocks::build_html_body` on `BlockEditor::to_blocks`; `body_is_html` is always true. `MailSent`/`DraftSaved` events are routed back through `AviaryApp.composes: Vec<ComposeHandle>` (`window: Option<WindowHandle>` — `None` pour l'inline — + weak entity keyed by `compose_id`).
- `block_editor.rs` (+ `block_editor/{clipboard,emoji,history,input_actions,links,mentions,proofreading,remote_images,render,tables,toolbar}.rs` — `proofreading.rs` = orthographe hors ligne + LanguageTool, `history.rs` = annuler/rétablir par instantanés, `tables.rs` = tables) — **éditeur WYSIWYG par blocs** (façon Notion) partagé par les trois surfaces du composer, panneau de réponse compris. Un `Entity<BlockInputState>` local (`ui/components/block_input.rs`) par bloc textuel (paragraphe/titre/citation/code) ou par item de liste, stylé au rendu. `BlockInput` possède l’IME, la sélection, le presse-papiers, les highlights, les menus de correction, la complétion emoji et la navigation verticale visuelle nécessaires à l’éditeur ; `components/display_map.rs` lui permet d’afficher autre chose que ce qu’il contient (repli de la destination d’un lien) : les offsets vivent alors dans deux espaces, *source* (document, curseur, presse-papiers, IME) et *affichage* (`TextLayout`), et chaque appel au layout convertit ; il évite de modifier l’`InputState` générique de gpui-component. Les touches structurantes (Entrée = scission, Retour arrière à l'offset 0 = fusion/dé-stylage, Tab = indentation de liste, ↑/↓ aux bords = bloc voisin) sont des **actions de l'input capturées sur un ancêtre** (`capture_action` + `cx.stop_propagation()`) ; les préfixes markdown (`# `, `- `, `> `, `---`, ``` ``` ```) transforment un paragraphe à la volée quand le curseur est juste derrière le préfixe (`BlockInputEvent::Change`). **Sélection multi-blocs** façon Notion : glisser au travers de plusieurs blocs (ou Maj+clic, ou Échap = bloc courant, ou Ctrl+A ×2) surligne des blocs entiers ; le conteneur prend alors le focus et son key context `BlockEditor` (bindings enregistrés par `block_editor::init` dans `ui::run`) route Ctrl+C/X (markdown vers le presse-papiers), Suppr/Retour arrière et Échap ; un collage multi-blocs dans un paragraphe re-scinde en vrais blocs (`markdown_to_blocks`). Le presse-papiers système ne transporte que le markdown : les images inline d'un copier/couper de blocs voyagent par l'annexe interne `CLIP_IMAGES` (réinjectées au collage si le texte collé correspond au dernier copier — y compris entre composers du même processus) ; l'aperçu du composer passe par `preview_markdown`, qui réécrit `cid:`/`bytes://cid-` vers le registre d'images. L'éditeur **possède les images inline** du brouillon (`images()`), rendues via `inline_images::register_bytes` : insertion par le bouton « Image » du composer / le menu de bloc (`prompt_insert_image*`, extensions filtrées par `image_mime_for_path`), collage d'une image bitmap du presse-papiers (`ClipboardEntry::Image`, supporté par gpui sous Wayland/X11), **poignée de redimensionnement** au survol (largeur mesurée au rendu par `on_children_prepainted` comme point de départ, `width` injecté dans le HTML sortant par `build_html_body`), et suppression d'un bloc image qui retire la pièce jointe devenue orpheline. **Les images d'un collage sont adoptées** (`remote_images.rs`) : un `<img src="https://…">` collé partirait sinon en lien externe, cassé chez le destinataire dès que l'hôte disparaît et signalant l'ouverture du courriel. Chaque source est réécrite en `cid:` sur une `InlineImage` du brouillon ; les charges `data:` (base64) sont décodées sur place, les distantes téléchargées par le runtime (`Cmd::FetchInlineImage`, routé en retour par `editor_id` = le `scope` de l'éditeur). L'URL d'origine de chaque cid en vol est conservée (`pending_remote_images`) : un échec la rétablit, et `build_outgoing` la remet dans le HTML sortant si l'envoi devance le téléchargement — jamais d'image inline vide chez le destinataire. **Annuler/rétablir au niveau document** : snapshots complets (`Snapshot` = kinds + images) empilés avant chaque opération structurelle (`push_undo`) et à chaque rafale de frappe (`note_text_change`, coalescence 1,2 s par input, état « d'avant » = `mirror` rafraîchi à chaque rendu) ; Ctrl+Z/Ctrl+Maj+Z utilisent les actions locales de `BlockInput` et sont aussi bindés dans le contexte `BlockEditor` quand la sélection de blocs a le focus ; la restauration reconstruit les blocs et focalise le premier bloc modifié. **Navigation ↑/↓ inter-blocs** : l'action locale `MoveUp`/`MoveDown` est capturée puis vérifiée en différé (`cx.defer_in`) — l'input navigue en lignes *visuelles*, donc « en butée » se détecte par un curseur resté immobile ; le saut atteint aussi les blocs non textuels (image/séparateur/message d'origine) en les sélectionnant, et ↑/↓/Entrée déplacent/ouvrent la sélection ensuite. **Liens** (`links.rs`) : un lien est du markdown dans le texte du bloc — toujours `[libellé](url)`, même quand le libellé n'est que l'adresse répétée : `<url>` s'afficherait pareil une fois replié, mais son texte visible *est* sa destination, donc le renommer sur place casserait le lien. Rien de nouveau n'est persisté ni sérialisé, `build_html_body` produisant déjà l'`<a href>` (verrouillé par `both_link_forms_reach_the_outgoing_body_as_anchors`). Le libellé est coloré (`theme.link`) et souligné par `inline_format_highlights`, le reste estompé comme les autres marques. Le libellé porte `theme.link` dont la **luminosité est alignée sur celle du texte du corps** (`readable_link_color`, bornée à [0,35 ; 0,82] pour que la teinte survive à un texte quasi noir ou quasi blanc) : `primary` est choisi pour des boutons, posé sur un fond, et celui d'OneDark (0,66) est plus sombre que son propre texte (0,71), si bien qu'un lien non corrigé paraît éteint. La teinte et le soulignement suffisent à le distinguer. La destination porte `theme.muted_foreground` — une **couleur**, pas un `fade_out` : l'estompage mélange vers le fond, ce qui la rendait quasi invisible sur canevas sombre (luminosité ≈ 0,24 contre 0,18 pour le fond) et délavée sur blanc. Elle n'est de toute façon à l'écran que lorsque le lien est déplié, donc quand on la lit ou l'édite. Le libellé seul est affiché : les crochets et la destination sont **repliés** (`foldable_ranges` → `DisplayMap`, voir `components/`) et reviennent dès que le curseur ou la sélection touche le lien — y compris collé contre l'un de ses bords, sans quoi il serait inéditable. **Un bloc sans focus replie tout** : il conserve son caret là où il était, donc s'en remettre à la sélection laisserait le lien déplié après avoir quitté le bloc. **Ctrl+K** (bindé sur les contextes `BlockEditor` *et* `BlockInput`, l'action étant inconnue de l'input elle remonte sans capture) et le bouton « Lien » de la barre d'outils ouvrent un dialogue à deux champs : il **modifie le lien sous le curseur** s'il y en a un (bords inclus), sinon il habille la sélection ; une adresse vide dégrafe le lien en conservant son texte. Coller une URL nue la transforme en lien dans n'importe quel bloc textuel (item de liste compris), en habillant la sélection s'il y en a une. Les URL nues ne sont **pas** détectées dans le texte déjà saisi : pulldown-cmark implémente CommonMark, qui linkifie `<url>` mais pas `url`, si bien qu'un style appliqué sans les chevrons promettrait un lien que l'envoi n'aurait pas produit. Entrée/sortie du document par `BlockKind` (`from_markdown`/`to_blocks`/`to_markdown`/`build_html`, `insert_kinds` pour les modèles).

  **Expéditeurs bloqués** (`GlobalSettings.blocked_senders`) : le courrier de ces adresses part vers les indésirables dans `events/mailbox.rs::on_new_messages`, **avant** les notifications de bureau et le filtre de pertinence par compte. Filtrage **local et non poussé au serveur** (Graph n'a pas de `blockedSenders` en v1.0, les filtres Gmail sont derrière `gmail.settings.basic`, IMAP n'a rien) et **global plutôt que par compte** : c'est Aviary qui l'applique, pas un serveur, donc l'unité est la personne et non la boîte. Seule l'adresse nue en minuscules compte (`settings::normalized_sender`) ; un `From` sans adresse n'est jamais bloqué. Classements silencieux via `send_batch_now`, mais agrégés en un seul toast d'échec.
- `snooze.rs` — **reporter un message à plus tard**. Une échéance est un état côté Aviary (`AccountSettings.snoozed_messages`), rangé à côté de l'épinglage : aucun provider n'expose de report partagé par les trois backends. **Le message ne bouge pas** — rien ne part au réseau, et surtout **son identifiant ne change pas**, ce qu'un déplacement IMAP ne pourrait pas promettre (`UID MOVE` en émet un nouveau, le repli COPY+EXPUNGE n'en renvoie aucun). `filtered_message_headers` masque ce qui est reporté ; le filtre « Reportés » (`MailboxState.show_snoozed_only`, non persisté) est le seul endroit où ces messages et leur échéance s'affichent. Réveil par **tick de 30 s** (`WAKE_TICK`), première passe avant le premier tick pour rattraper une échéance tombée application fermée ; le réveil marque non lu, silencieusement et par lot. **L'échéance remplace la date de réception sur la ligne** au lieu de s'y ajouter : les hauteurs sont indexées par `MsgEntryVariant`, un élément de plus serait une variante que rien ne mesure.
- `addresses.rs` / `inline_images.rs` — champ de destinataires + popup de contacts contrôlé localement, et registre d’images utilisé par les aperçus de l’éditeur de blocs (servi par l’`AssetSource` et `CidHttpClient`) ; voir « Écarts résolus » en bas.
- `blitz_body.rs` (+ `blitz_body/{actor,bands,element,events,net,outlook,paint,selection,theme,tests}.rs` — le parent ne garde que l'état partagé : `Entry`, `BlitzCache`, les clés de cache, `Job` et les types qui traversent la frontière de thread ; `element.rs` = élément gpui, liens et zoom, `bands.rs` = bandes et pompes, `events.rs` = souris/clavier et copie, `actor.rs` = thread du document, `paint.rs` = mise en page et rasterisation) — mode **« Fidèle »** du lecteur (`BodyViewMode::Blitz`) : le HTML d'origine est rendu par le moteur **Blitz** (Stylo + Taffy + parley, crates `blitz-{dom,html,paint,traits}` 0.3.0-beta), rasterisé en CPU (`anyrender_vello_cpu`) puis affiché comme image (`RenderImage`, RGBA→BGRA, découpe en tuiles de 2048 px pour les limites de texture ; hauteur plafonnée à 16384 px physiques). Le document reste **vivant et interactif** : `HtmlDocument` n'est pas `Send`, donc chaque rendu vit sur son **thread acteur** (`spawn_doc_thread` — rend, envoie `Rendered` + `LiveDoc{tx}` par oneshot, puis boucle sur les `DocCmd` ; la fermeture du canal à l'éviction termine le thread). Les événements souris gpui sont convertis en `UiEvent` Blitz (coordonnées = position − origine mémorisée au prepaint, en px logiques) et poussés dans `Entry.pending` ; une **pompe** (une par entrée, `pump_running`) les envoie par lots au thread acteur et applique le retour : curseur (`get_cursor` → I-beam/main), re-rasterisation seulement si une sélection est **visible** avant/après le lot (un clic simple — lien, zone vide — ne repeint rien) et seulement pour les **tuiles intersectant la zone touchée** (`PaintState` suit le trajet du pointeur + l'étendue de la sélection ; `paint_tile_band` rend une bande en réglant `set_viewport_scroll` — le painter culle le reste ; marge `DIRTY_MARGIN_CSS`, repli plein rendu si la zone couvre tout). vello_cpu tourne avec la feature `multithreading` (rayon). Le survol ne coûte qu'un hit-test. On obtient ainsi la **sélection de texte** (surlignage peint par le moteur, Ctrl+C copie via `get_selected_text`, Échap efface — focus clavier par `track_focus` + clic) et les **liens cliquables** (clic d'ancre → `NavigationProvider` (`OpenLinks`) → `open::that_detached`, schémas http/https/mailto seulement). Re-rendu (sélection perdue) quand la largeur mesurée change (`on_children_prepainted`), cache global `BlitzCache` (FIFO 6 entrées, clé = message + hash du corps + signature des images inline + « images distantes »). Ressources via un `NetProvider` maison : `cid:` depuis `Message.inline_images`, `data:` décodées localement, `http(s)` seulement si « images distantes » est actif — la requête part sur le runtime tokio de l'app via `runtime::TOKIO_HANDLE` ; le rendu initial boucle `resolve` tant que des ressources sont en vol (compteur `pending`, timeout 8 s). Toujours `ColorScheme::Light` + fond blanc (fidélité email). Tests : `cargo test blitz_body` (rendu, sélection par glisser, clic de lien, data-URI).
- `settings.rs` — persisted `Settings`/`GlobalSettings`/`AccountSettings`, stored as pretty JSON at `~/.config/aviary/settings.json`.
- `theme.rs` — light/dark via `Theme::change` + the OneDark palette applied onto `ThemeColor` fields.
- `icons.rs` — icons are **lucide SVG files** under `assets/icons/`, embedded via `rust-embed` and served through the `AssetSource` in `ui/mod.rs` (gpui-component resolves its own `IconName`s against the same folder). `icons::app_icon("mail")` loads `icons/mail.svg`.
- `util.rs` / `datefmt.rs` — pure helpers (address parsing, account colors, localized dates).

gpui conventions used throughout: state that outlives a frame lives in `Entity<T>` (e.g. every text field is an `Entity<InputState>` created once and kept on the struct — never recreate them in `render`); `cx.listener(...)` for handlers that mutate the view; `cx.subscribe_in` for `InputEvent`s (subscribe **once**, in the constructor, never in `render`); toasts via `window.push_notification(...)` (requires the `Root` wrapper, whose notification/dialog/sheet layers are re-emitted at the end of `AviaryApp::render`).

### Fenêtres secondaires

Le composer s'ouvre **par défaut dans le volet de lecture** (voir `compose.rs` ci-dessus) ; les fenêtres OS (`cx.open_window` + `Root`) servent au détachement, aux composers supplémentaires et aux événements calendrier. Handles (`Option<WindowHandle<Root>>` + `WeakEntity<view>`) are kept on `AviaryApp` so `handle_event` can route runtime replies (`MailSent { compose_id }`, `EventCreated { request_id }`) to the right compose and close it (`window.remove_window()` / libération du volet). Message previews and replies stay **inside** the main window (tabs + reply panel, see `viewer/` above) — no OS windows for those.

### Storage paths

- Config dir: `directories::ProjectDirs::from("be", "acetics", "aviary")` → typically `~/.config/aviary/`
- `settings.json` — UI settings (serde JSON)
- `session.json` — état léger de l'interface et brouillons en cours ; les messages sélectionnés, onglets et cartes de réponse n'y sont que des `MessageRef { account_id, id }`. `Cmd::LoadCachedMessage` les recharge depuis SQLite sans attendre l'authentification.
- `mail-cache.sqlite3` — en-têtes et métadonnées de corps, avec images inline et pièces jointes dans des tables `BLOB`. Le cache est jetable : un changement de `SCHEMA_VERSION` recrée le schéma au lieu de migrer les anciennes représentations. Il porte une colonne `conversation_id` et la requête d'agrégation `conversation_totals`, qui alimente le compteur des groupes de la liste (`Evt::ConversationTotals`) : compter dans l'UI ferait grimper le compteur au fil du défilement, la page chargée étant plus courte que le fil. Il porte aussi l'**index plein texte** `messages_fts` (FTS5 `content=''`, `contentless_delete=1`, tokenizer `unicode61 remove_diacritics 2`) : l'indexation est explicite côté Rust (`index_message`, le corps étant d'abord nettoyé par `searchable_body_text`), la suppression passe par le trigger `messages_fts_delete`, et la recherche est cache-first comme le listage — voir `CLAUDE.md` pour le détail.

Le champ de recherche est analysé une seule fois par `src/search_query.rs` (`SearchQuery`, donnée pure) ; chaque consommateur en fait son propre dialecte (FTS5, `q` Gmail, KQL Graph, `SEARCH` IMAP). Les opérateurs existent en français et en anglais, un opérateur inconnu reste du texte libre, et `SearchQuery::matches` est réappliqué aux résultats des providers car chacun ignore ce qu'il ne sait pas exprimer.
- `pending_tokens.json` / `accounts/*.json` (chmod 600 on Unix) — pending and per-account credentials

### Auth

`auth/microsoft.rs` implements the Microsoft device-code flow against `login.microsoftonline.com/{tenant}`. The scope string is hardcoded (`SCOPE` constant) and includes `offline_access Mail.ReadWrite Mail.Send Calendars.Read People.Read User.Read`. If you add a Graph endpoint that needs a new scope, update `SCOPE` and the user will need to re-auth.

`auth/google.rs` implements Google's OAuth 2.0 installed-app flow with **PKCE + loopback redirect**. `auth/imap.rs` stores the IMAP/SMTP password in the OS keyring and the server config in the per-account token file.

The unified `Tokens` struct stores `provider: Provider`, the issuing `client_id`, and `tenant` (Microsoft-only). Each account stores its provider on `BgAccount` and `BgAccount::ensure_auth` dispatches refresh via `match self.provider`. `Cmd::StartLogin` is Microsoft-only; `Cmd::StartGoogleLogin` / `Cmd::StartImapLogin` trigger the other flows.

### Provider abstraction (`src/providers/`)

`providers/mod.rs` exposes the unified API surface as methods on **`Session<'a>`** — an enum `{ Graph { client, token, tenant }, Gmail { client, token }, Imap(ImapAuth) }` pairing a backend with its live credentials, so a provider/credentials mismatch is unrepresentable. Runtime tasks build one per call: `let Some(auth) = account.auth_or_report().await else { return }; account.session(&auth).list_folders().await` (`auth_or_report` = `ensure_auth` + the standard `Evt::Error` reporting; tasks that emit a specific error event — send, event create — call `ensure_auth` directly). During login, before a `BgAccount` exists, `auth_flow.rs` constructs the `Session` inline. Runtime modules only call the `Session` surface; **never** call `providers::graph::*` / `gmail::*` / `imap::*` directly from runtime code or the UI. The shared `OutgoingMessage` / `NewCalendarEvent` borrow types live in `providers/mod.rs`.

**Move aliases** (`ARCHIVE_FOLDER_ALIAS` = `archive`, `JUNK_FOLDER_ALIAS` = `junkemail`, `INBOX_FOLDER_ALIAS` = `inbox`) let one UI call site work across the three providers: Graph treats them as well-known folders, Gmail translates them into label mutations (archiving = dropping `INBOX`, since it has no Archive label), and IMAP resolves them against the account's own folder list (`well_known_move_alias`) because it infers well-known names from `LIST` attributes rather than being told them — failing with a translated error when the server has no such mailbox. The UI passes the account's real folder id when it knows it (`AviaryApp::well_known_folder_id`) and the alias otherwise. **Junking a message reports no source folder**, exactly like archiving: Graph and IMAP ignore it, but for Gmail the source is the label to *remove*, and passing the folder on screen would strip that label while leaving the message in the inbox. « Non indésirable » is the one action that does report a source, since Gmail needs `SPAM` dropped explicitly. Both are locked by tests in `gmail/messages.rs`.

### Microsoft Graph (`providers/graph/`)

`providers/graph/*.rs` is the *only* place that should know about Graph JSON shapes. Pagination uses Graph's `@odata.nextLink` — `fetch_messages_page` follows those links.

Incoming HTML mail is converted to Markdown via `html_to_markdown_rs::convert(html, Some(html_md_options()))`. The options set `extract_metadata: false` and `exclude_selectors: ["head", "meta", "title", "link", "style", "script"]` — this is what prevents the Outlook CSS preamble and Word/Apple meta tags from leaking into the rendered body. Keep that selector list when adjusting the helper. Inline `cid:` references in the converted markdown are rewritten to `bytes://cid-{cid}`; le mode Markdown les rétablit en `cid:` avant de les confier au `NetProvider` Blitz avec les `Message.inline_images`.

### Gmail / Google (`providers/gmail/`) et IMAP (`providers/imap/`)

Mirror `providers/graph/` 1:1 in API surface but map each protocol's idioms to Aviary's domain types (labels ⇔ folders, `UNREAD`/`STARRED` labels ⇔ read/flag state, `threadId` ⇔ `conversation_id`, opaque `nextLink` blobs for pagination, RFC 822 assembly for send, soft-delete via trash). See the module docs in each backend for details. **IMAP n'a pas d'identifiant de conversation** : `derived_conversation_id` le dérive du `Message-ID` *racine* (tête de `References`, repli `In-Reply-To` puis identifiant propre), calculable depuis les seuls en-têtes d'un message — donc stable d'une page de listing à l'autre. Pas de repli par sujet. `list_thread` reconstruit le fil par SEARCH sur la boîte de réception et les envoyés uniquement. Comme les requêtes de fil traversent les dossiers (Graph aussi), une même lettre revient en deux exemplaires — copie envoyée et copie reçue — avec deux identifiants provider mais un seul `Message-ID` : `MessageHeader::internet_message_id` porte ce dernier et `viewer::thread_without_duplicates` s'en sert pour ne pas relister le message affiché.

### Blocs (`src/blocks/`)

`Block`/`BlockKind` document model (used by `model::Signature`/`Template` persistence and edited directly by `ui/block_editor.rs`) and the markdown/HTML serialization (`markdown_to_blocks`, `blocks_to_markdown`, `build_html_body`). `build_html_body` is the single producer of outgoing HTML — compose, event descriptions and signatures all go through it.

**`BlockKind::Signature`** is the signature *as inserted in a draft*, distinct from `RawHtml`: it carries the signature id, its name at insertion time and its HTML rendered once and for all (`compose::signature_block_kind`). Frozen at insertion for the same reason as `OriginalMessage`: a draft must not change because Preferences were edited since. `build_html_body` wraps the fragment in `<div class="aviary-signature" data-aviary-signature-id="{id}">` — the class other clients also use, and the id (never the name, which is the user's own wording) so a reopened draft can identify it.

**`html.rs` is the return path.** A draft saved on the provider comes back as HTML; `html_to_blocks` rebuilds the document by walking the DOM (`scraper`) instead of going through the reader's HTML→Markdown conversion, which is tuned for *reading* (it unwraps layout tables, drops Aviary's own class names and rewrites `cid:` to `bytes://`). Structure the editor can hold becomes a real block — headings, nested lists, quotes, code, tables, dividers, inline images with their width, inline marks written back as Markdown even when the source expresses them as CSS on a `<span>`; what it cannot hold stays opaque (`Signature`, `OriginalMessage`, `RawHtml` for a table of structured cells) rather than being flattened. Gmail's `gmail_signature`/`gmail_quote` and Outlook Web's `<div id="divRplyFwdMsg">` (whose quote lives in its *siblings*) are recognised too.

### Linux-only bits

`tray.rs` (system tray via `ksni`) is gated by `#[cfg(target_os = "linux")]`. The tray runs on its own thread and feeds `TrayAction`s back through an mpsc channel drained by a gpui foreground task (`AviaryApp::handle_tray`). Notifications (`notify.rs`, via `notify-rust`) work everywhere.

`ksni` is declared with `default-features = false, features = ["blocking", "async-io"]`. **Do not** re-enable the `tokio` feature: it would set `zbus/tokio` and — via Cargo feature unification — flip every other zbus consumer into tokio mode, which panics from threads without a runtime entered. The spawn pattern is `use ksni::blocking::TrayMethods; tray.spawn()`.

### Single instance and `mailto:` (`src/single_instance.rs`, `src/mailto.rs`)

The desktop entry registers `x-scheme-handler/mailto` with `Exec=aviary %u`, so **every click on a mail link starts a new process**. Aviary owns a `session.json`, a `settings.json` and two SQLite databases that expect a single writer, so `main()` claims the session through a Unix socket in `XDG_RUNTIME_DIR` **before opening anything**. The first process binds and becomes the primary; later ones connect, send one JSON line and exit without opening a window.

The file's existence proves nothing — a crash leaves it behind — so *connecting* is what proves an instance is alive: `acquire` tries `connect` first and only unlinks after a refusal. A lost `bind` race retries `connect` once; any other failure is logged and startup continues without the guarantee, since refusing to launch would be worse. `acquire_at` takes the path as a parameter so the handover is tested end to end.

The primary's own launch request goes through the same channel as later ones, giving the UI a single path to serve (`AviaryApp::handle_external_request`, pumped like the tray). Every request calls `window.activate_window()`, or a tray-minimized window would swallow the mailto while staying hidden.

`mailto.rs` is the RFC 6068 parser shared with `mailto:` anchors clicked in a message body (`blitz_body/element.rs::mailto_compose_init`, replacing `mailto_recipients`, which read recipients only — so a link carrying `?subject=` opened an empty message). Two deliberate restrictions, because the URL comes from a web page or an email rather than the user: **`attach` and unknown headers are ignored** (honouring it would let a page name a local file and have it mailed out) and **control characters are stripped** (`%0A` in a subject is the classic header injection). `+` is not decoded as a space — RFC 6068 percent-encodes, it is not form encoding, and `user+tag@example.com` is far too common to mangle. A `mailto:` is never handed back to the system opener, even an empty one: Aviary may be the registered handler, so delegating would ask the desktop to relaunch us.

### gpui / gpui-component — pièges connus

- gpui renders through **blade (Vulkan)** on Linux: `shell.nix` must keep `vulkan-loader` in `LD_LIBRARY_PATH` (plus wayland/x11/fontconfig/freetype).
- All SVG icons referenced by gpui-component's `IconName` must exist in `assets/icons/` (embedded by the `Assets` struct in `ui/mod.rs`); missing files log render errors. When using a new built-in component, check which `IconName`s it draws.
- **Les runs de highlight doivent être triés et disjoints.** `StyledText::with_highlights` délègue à `compute_runs`, qui parcourt les plages *dans l'ordre donné* et convertit chacune en **longueur** de run consécutive : une plage non triée fait régresser son curseur interne et décale tout ce qui suit (symptôme : le texte après un lien se colore). Deux plages qui se chevauchent produisent le même effet. Or `inline_format_highlights` émet naturellement (contenu, délimiteur gauche, délimiteur droit) — non trié — et la correction orthographique peut recouvrir une marque inline. Tout doit donc passer par `combine_highlights`, qui trie les endpoints et fusionne les styles superposés. Un délimiteur **symétrique** (`**gras**`) retombe juste par coïncidence de longueurs, ce qui a masqué le problème jusqu'aux liens (`[` d'un côté, `](url)` de l'autre). Verrouillé par `combined_highlights_are_sorted_and_disjoint`.
- `Theme::change(mode, …)` resets colors from the registry; apply palette overrides (OneDark) **after** it, then `cx.refresh_windows()` (see `ui/theme.rs::apply`).
- `cx.theme()` borrows `cx`; when a render closure later needs `&mut cx`, clone the theme first (`let theme = cx.theme().clone();`).
- `TextView::markdown/html` need `(window, cx)` and parse asynchronously; `.scrollable(true)` requires a fixed-height parent.
- Fonts: Inter / JetBrains Mono / Noto Color Emoji are embedded; gpui registers them in `ui::install_fonts` and Blitz registers the same families in its own Fontique context. Vello CPU/Glifo renders Noto Color Emoji’s CBDT/PNG strikes; `theme.font_family = "Inter"`. `cosmic-text` is patched locally so its Linux fallback tries Noto Color Emoji before monochrome symbol coverage from Noto/DejaVu Sans.
- **Cohabitation gpui + Blitz/Stylo** (deux pièges d'unification de features) : (1) gpui active `log/kv_serde`, ce qui met `serde_fmt` dans le graphe et son `impl From<serde_fmt::Error> for fmt::Error` rend ambigu le `?` des impls générées par `derive(ToCss)` de Stylo → `stylo_derive` est **vendorisé et patché** dans `patches/stylo_derive/` (`[patch.crates-io]`, `?` remplacés par des `match` explicites — même approche que ServoKit). En cas de montée de version de Blitz/Stylo, re-copier la nouvelle version du crate depuis `~/.cargo/registry/src/` et réappliquer la transformation dans `to_css.rs`. (2) gpui active `yeslogic-fontconfig-sys/dlopen` (via font-kit) → la dépendance directe `fontique` avec la feature `fontconfig-dlopen` aligne fontique (tiré par blitz-dom/parley) sur cette API, sinon ses imports fontconfig échouent à la compilation.
